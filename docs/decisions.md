# Decision log

Every design decision that shapes the project, in one place. Decisions are never deleted. When one
changes, the old entry is marked **superseded**, with a pointer to its replacement.

Status values:
* **active**: agreed and in force;
* **proposed**: suggested by the assistant, awaiting review;
* **superseded**: replaced by a later decision.

Source: *brief* = original task brief; *review N* = user feedback at review N; *impl* = made during
implementation and accepted at a later review.

| D32 | **One exit announcement before the physical tunnel exit C.** Replaces the navigation event inside B–C with two leads (D14, D26). | D34 | **Calibration error = residual error of the phone-to-vehicle orientation the estimators use.** `ScenarioConfig.calibration` (enabled, yaw/pitch/roll error in vehicle axes; default off; schema v6). | D37 | **Traffic = shared primitives anchored to B/C.** `ScenarioConfig.traffic` (schema v8) selects free flow, portal slowdown (T1), tunnel speed limit (T2), stop-and-go (T3), exit queue (T5) or congested flow (T6); T4 incident stop skipped by decision. Stops end with a constant-jerk manoeuvre (j = a²/2v), so speed and acceleration reach zero together. Seeded randomness on positions, durations and speeds (`jitter`, own seed stream). Truth, IMU and GPS follow from the same motion; free flow is bit-identical to before. UI: *Traffic in the tunnel* panel. Estimators unchanged. | active | review 6 |
| D38 | **Simulator scope frozen after two realism additions**, both optional and off by default (bit-identical results): (1) *IMU bias drift*, a per-axis first-order Gauss-Markov bias on top of the constant bias (defaults 0.5 mg / 5 mdps, τ = 300 s; in-run instability and temperature); (2) *GPS degradation before the portal*, ramping up over the last ~150 m before B: extra correlated position error (8 m, τ = 5 s), extra speed noise (0.5 m/s) and multipath jumps (5 %, 25 m), with the reported accuracy growing except for the jumps. | D39 | **Map grade = optional, exact map information for the estimators.** `ScenarioConfig.map_data.road_grade` (schema v9; default off, bit-identical results). When on, `RouteMap.road_grade` carries the road grade every 10 m along the map route: the true grade at the point of the driven path closest to each map point (the map is assumed correct, by user decision; map errors stay in limitations.md). The map carries the grade itself, as provider slope attributes do, not heights: differentiating heights over map distance gave false grade dips where the driven path cuts a polyline corner, and those biased the calibration (found during validation). | D40 | **Positioning pipeline with an alignment stage: observations → alignment → estimator.** The alignment stage (`positioning/alignment.py`) is the first positioning step: it turns the raw phone IMU into vehicle-axis samples (all three axes, noise and bias kept, nothing filtered; the estimated gyro bias removed from the yaw rate; φ_cal attached), or None before an orientation is known. ## Proposed (historical text, adopted above)

| ID | Proposal | Why |
|---|---|---|
| PD1 | Move observation types (`ImuStream`, new `GnssStream`, `RouteMap`, `NavigationEvent`) into a neutral `throughtunnel/observations.py` that imports no simulator module. Enforce the boundary with a subprocess test: importing `throughtunnel.positioning` must not load `vehicle`, `road`, `scenario` or `sensors`. | Today `ImuStream` lives in `sensors/imu.py`, which imports `GroundTruth`, so positioning code would load the truth module just by using the observation type. |
| PD2 | GPS measures the **phone** position (the antenna is in the phone), and evaluation compares estimates with the true **phone** position (reference point + lever arm), evaluated exactly at estimate timestamps. | Truth currently refers to the rear-axle reference point; with a lever arm the two differ by up to ~2–3 m. |
| PD3 | Along/cross-track errors are defined against the **true path tangent at the true position at the same timestamp**. Event crossing times come from projecting map-defined points onto the true path. | The map polyline and the smoothed truth path have different arc lengths (corner cuts up to ~4 m, ~1 m per 3 km). A single, truth-side frame avoids mixing parametrisations. |
| PD4 | The GPS loss and reacquisition boundaries are **not perfectly sharp**: randomised loss point / short degradation zone before B, randomised reacquisition delay after C. | A deterministic cut-off exactly at B tells the estimator the exact entrance time, an unrealistically perfect along-track anchor. |
| PD5 | Phone mounting for the first baseline: estimate levelling (gravity) from approach data. Either **declare** the yaw misalignment as an estimator assumption, used only in aligned-mount scenarios, or **estimate** it from GPS speed/bearing vs. gyro and accelerometer during the approach. Report which mode was used. | The mounting is hidden truth. Its yaw part is only observable when the approach has turns or speed changes, and levelling errors act like accelerometer bias (1° ≈ 17 mg). |
